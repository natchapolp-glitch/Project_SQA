- createNumber: valid integer string → Long; valid decimal string → Double; malformed numeric string (e.g. "not a number") → should throw ParseException, not NumberFormatException; boundary values like Long.MAX_VALUE/MIN_VALUE and overflow beyond long range (should fall back to Double or BigInteger per contract).
- createValue(String, Class): dispatch correctness for each supported type token (Number.class, String.class, Object.class, Class.class, File.class, Boolean.class if supported) and unsupported class type → ParseException.
- createValue(String, Object): behaves identically to createValue(String, Class) when Object is actually a Class instance; passing non-Class Object should throw ParseException per contract (not ClassCastException).
- createClass: valid fully-qualified class name succeeds; invalid/nonexistent class name → ParseException (not ClassNotFoundException leaking out).
- createURL: valid URL string succeeds; malformed URL string → ParseException (not MalformedURLException leaking).
- createObject: valid no-arg-constructible class name succeeds; invalid/non-instantiable class name → ParseException.
- createDate: currently unsupported/always throws UnsupportedOperationException — verify this documented behavior remains.
- createFile/createFiles: basic valid path string returns File/File[] without throwing; no strict existence check expected.
- Ensure no undeclared runtime exceptions (NumberFormatException, ClassCastException, MalformedURLException) escape public API — all must be wrapped as ParseException where documented.
- Empty string and null input handling for createNumber/createClass/createURL should be checked against ParseException expectations rather than throwing unchecked exceptions.
